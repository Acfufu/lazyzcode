# ADR-0023: 多 provider 计价口径——单位明文、枚举式覆盖、源可引

日期：2026-09-21 ｜ 状态：已拍板（0.2.2 拍板总账 Q1/Q9，goal v022-bat1-instrument）｜
关联：决策 #16（经验测量而非声明式配置）、ADR-0003 修正节（本地事实表人工维护先例）、
§⑯（水位档位适配：防再议注记同族）、V021-ADJ-55（水位 CASE 表只认两枚 GLM model_id）、
`core/ratelimit.js` 的 `PEAK_WINDOWS`（手维护事实表 + 源注释的模板）

## 背景

水位/成本折算的系数表原先只列 `GLM-5.3-Flash` 与 `GLM-5.3`，其余 model_id 按 `ELSE 0`
计 0。0.2.1 的五轮双审（V021-ADJ-55）只落了**披露句**——读数是下界这件事变得可见，但
读数本身仍只覆盖 GLM。0.2.2 棒1 实测：本机 5h 滚动窗内 deepseek 282 行、GLM 侧近乎为零
——**水位门对本仓真实用量完整空转**（读数 0.15~2.2 积分，对照警戒线 1600 与 drive 默认
积分硬顶 400）。这不是显示问题，是执法问题。

同时暴露一个结构性缺陷：水位 SQL 把同一张系数表以**字面量手抄**了一遍，于是「改 core
侧就以为改完了」的半修窗口天然存在（ADJ-55 的成因）。

## 决策

1. **单位明文：元/百万 token（人民币，官方价目页）。** 三列顺序 input / cache-read /
   output。GLM 两行沿用既有数值不回改（本就同量级）。此前注释只写「积分/百万 token」而未
   声明单位——单位不明，外部 provider 的 CNY 价目就无从落表。

2. **表内数值取官方高峰价，非高峰由时段乘数统一承担**（`PEAK_MULTIPLIER=1.0` /
   `OFF_PEAK_MULTIPLIER=0.5`）。DeepSeek 官方价目恰好同构（高峰=空闲×2），故两家共用一条
   时段规则，不为单家另造乘数。

3. **覆盖面前提是「源可引」**：只有拿得到 official 页面并逐字核过的 model_id 才入表。
   **不放宽为族前缀匹配、不做模糊/后缀匹配**——那会把不该计价的 model_id「猜」进表内，
   正撞「绝不猜系数」红线。代价是新 provider 前缀落到表外（计 0 + 具名披露）；**这正是
   安全的失败方向**：宁可读数偏低并如实标注，不可虚高。

4. **匹配=小写化后精确等值**（`MODEL_ALIASES`）。小写化解决账本里 GLM 的大小写双形态；
   别名表逐条列出实见形态（含 provider 前缀形态与官方注明的旧标识），补表=加一行。

5. **水位 SQL 由系数表生成**（`buildWaterlineSql()`），不再手抄。表即单源，别名与系数
   零漂移；`test/cost.contract.test.js` 有专门的漂移守卫测试。`plugin/hooks/stop.js` 的
   自包含副本**仍是手工孪生**（钩子部署后脱离 `core/`，不能 import）——改表时须同步，
   两侧注释互为指路。

6. **披露句常驻**：读数是「计价子集上的下界」这一事实**不随窗口变**，故不再「表外有行才
   出声」（扩表后窗内可能恰好无表外行，整句会消失）。**具名**面在 `lzy loop cost` 的
   未计价行（全量账本口径，不随 5h 窗滑动）。

7. **查证记录写进表注释**：哪些源查过、结论是什么、为何不入表。2026-09-21 实查：MiniMax
   （`platform.minimaxi.com/document/{price,guides/pricing}`）只列语音套餐，无每百万 token
   价；MiMo（`platform.xiaomimimo.com` → `mimo.mi.com/docs/pricing`）为占位页。两者连同
   `muse-spark` 族维持表外并具名——**「查而无源」是结论，要留痕**，否则下一轮会有人再查一遍
   或干脆猜一个数。

## 后果与边界

- **水位门自此对主力用量生效**，读数会显著高于 0.2.1 时期——drive 的积分硬顶（缺省 400）
  与警戒线（1600）存在被触发的新可能。此为拍板时已知代价；阈值经 `LZY_WATERLINE_POINTS`
  覆盖，重定标须实测后另行拍板，**不得静默调门**（本棒 Known unknowns #1 的证伪途径）。
- 手维护表的固有边界：官方调价后表会漂移。沿 `PEAK_WINDOWS` 家法——表是「人工维护的已知
  事实」，不是测量；漂移只让读数偏差，不会让门做出错误动作之外的事（门是自参照经验线）。
- 计费账本无 provider 归属的**价格维度**：provider_id 只是渠道标识（broker/UUID 皆有），
  故计价按 model_id 而非 provider，避免把渠道当价目。
