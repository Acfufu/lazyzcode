# ADR-0040：全局用量追加互斥与累计快照

日期：2026-10-25。状态：本地实现，未发布；独立于工作区 SQLite 迁移与尚未通过的进程回收门。依据：[可靠性补丁计划](../plan-v061-reliability-patch.md) R0 账本协议／R3。

## 取舍

全局 JSONL 仍是消费记录，旧行保留。新增同目录 `.append-lock.sqlite` **只充当跨进程互斥**：没有表、事件、消费副本或第二权威；`BEGIN IMMEDIATE` 取得写锁，临界区结束 `ROLLBACK`，所有读、判重、差量重算和 JSONL 追加在锁内。用现有 Node ≥24 的内建能力，新增 npm 依赖为零。工作区 queue／dispatch／budget 的 `state.sqlite` 和事务顺序不变。

选择此机制是因为 PID 锁文件的崩溃回收、PID 复用与并发删旧锁容易拆开互斥。SQL 写锁交由 OS 释放，不自动删除或替换协调文件，不按年龄偷锁。等待上限默认 5 秒；超时具名失败，由权威运行档和 pending 回执保留补账入口。禁止同进程重入、异步回调、网络、spawn，以及持有工作区写事务时再取得该锁。

实现只使用 SQL 操作和连接关闭，沿用 [ADR-0039](0039-sqlite-store-boundary.md) 的运行时地板；协调文件以 0600 创建，目标必须普通文件。`appendFileSync` 刷盘后才报告成功。写中断的坏行只诊断和阻止继续追加，绝不自动改写历史。此处没有宣称 JSONL 与 SQLite 构成跨文件事务，也不承诺断电后的硬件持久性。

官方依据：[Node 24.0 SQLite API](https://nodejs.org/download/release/v24.0.0/docs/api/sqlite.html)、[SQLite 文件锁](https://sqlite.org/lockingv3.html)。这些文档解释机制；本仓实际并发、崩溃与平台行为由本次测试证明。

## 记录协议

- 原 `appendSandboxUsage` 继续追加差量事件，身份仍是 `(project, runId, instance, watermark)`；跨月统一判重，旧形记录保留原规则。
- 评审运行器与 harvest 改走累计快照入口。来源查询在锁外，锁内读取最新账本再重算差量；预览不作为提交依据。来源向量同时出现增加和减少时拒绝混算，旧快照已被完全覆盖时跳过。
- 新累计记录附带 `harvest.sessionIds`，其摘要必须与 instance 一致。会话集合增长时抵消已入账子集；集合完全不相交时视为同名 run 的另一实例。部分交叉、来源集合不足、旧实例没有足够身份凭据时具名阻塞，保留来源库核对，不猜测两次消费是否相同。缺实例的快照不能跨越已入账的具名实例；同事件身份出现增长读数也必须拒绝，不能静默丢掉差量。旧无 harvest 行仍按既有保守规则抵消，不重写历史。
- spool 是缺口回执，不是消费重放队列。文件名为项目／运行／事件身份的 SHA-256；相同明确事件可更新，缺身份时独立保留，避免 runId 复用覆盖。旧名回执仍计入诊断；成功追加不自动销掉历史 pending。
- 交付 provenance：字符串／null 保留原 `:delivery` 派生；JSON 对象／数组封装为 `{source: 原值, phase: "delivery"}`，不损失结构；其他形状显式拒绝。

## 验证与限制

检查涵盖真实四进程同事件竞争、不同项目／实例、旧新快照交错、来源集合扩展、持锁者强杀、丢确认后重放、坏行／符号链接、spool 兼容、真实 SQLite 来源的 harvest CLI 和 provenance 事务读回。平台和具体结果见[执行报告](../reports/reliability-patch-2026-10-25.md)。

所有写者必须使用新入口；旧安装实例并发写同一全局目录仍不受新锁约束。更新后应先结束旧写者，再开始补账。协调文件不可在仍可能存在写者时手工删除；这会产生两个互不相识的锁。没有身份信息的旧数据不能凭本次补丁自动恢复，遇到具名阻塞须从保留的运行档／来源库补齐事实。
