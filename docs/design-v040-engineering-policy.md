## 已确认决策

### Q1：版本边界

用户确认保留 0.3.1 两棒发布边界（交付编排 + 积分归因修正），其收口后另排 0.4.0 的策略、评审与评估工作。不将 0.3.1 剩余工作合并改名为 0.4.0。

### Q2：核心交付

用户确认 0.4.0 交付“机器闭环＋同期评估”：将必需检查、独立评审及未关闭阻塞发现接入统一放行判定，并用预先冻结的任务集检验收益。已有交付承诺的执法缺口单列为补齐项；不将其重新计为新增能力。评估设计与基线准备前置，不等实现结束后再挑选任务。

### Q3：LIGHT 的独立评审义务

用户选择 A：所有契约任务达到交付 A 前均须至少一次独立评审，LIGHT 不设低风险免审通道。评审范围可按任务缩小，复杂任务按风险增加职责；LIGHT 简化执行流程，不豁免交付条件。独立评审与 F 项断言—证据相关性的 comparator 职责分别建模，不能因已有 comparator 就默认独立实现评审已完成。此项落实既有 A 终点承诺，不另立追认旧决策的 ADR。

### Q4：受控独立评审执行

用户选择 A：由 `lzy` 发起独立评审会话，保存原始结果、关联会话与候选身份，消耗计入原任务预算；首轮输入不提供其他评审结论。复用 headless 原语，首个里程碑实测上下文隔离、结果采集、预算归因和中断行为。来源关联增强可追溯性，不宣称评审结论必然正确或能防止同权限进程篡改。评审执行失败不得被当作有效通过；能力探针未通过须明确阻塞，不暗中降为主代理自报。此架构取舍见 [ADR-0031](adr/0031-controlled-independent-review.md)，整体共识已在 Q12 确认。

### Q5：阻塞发现的关闭权

用户选择 A：实现代理只能将阻塞发现标记为“修复待复核”；须由独立复核者核对原发现、修复及当前候选证据后关闭，不要求复用原评审会话。认为是误报也须独立证伪。原发现与处置历史保留，下一轮未提及、改名或仅有测试通过均不构成关闭依据。

### Q6：评审按职责复用

用户选择 B：0.4.0 首版支持按评审职责与经过验证的依赖范围复用旧结果，并同时交付评审范围资格和对抗验证。证明变化不影响该职责时可沿用结果；依赖不明确则重新评审。旧评审保留原候选、输入和原始结论，每次复用另追加适用性判断，不能改写成对新候选执行过评审。此项单列实施与验收里程碑，见 [ADR-0032](adr/0032-review-scope-reuse.md)。复用评审不自动关闭阻塞发现，Q5 的独立复核义务仍有效。

### Q7：策略追加要求的撤销

用户选择 A：因影响变化而不再必要的额外检查或评审，可以经过独立复判后取消，记录影响变化、取消理由和复判依据。契约要求、现行分级的强制要求以及未解决的阻塞发现不能藉此删除；验收、授权、预算和 LIGHT/HEAVY 语义不变。此路径与复用不同：复用表示要求仍存在且旧结果仍适用，取消表示额外要求经复判不再适用。见 [ADR-0033](adr/0033-policy-obligation-reassessment.md)。

### Q8：评估与发布取舍

用户选择 A：允许用更高总成功成本换取可衡量的质量收益，不要求相对 0.3.1 成本下降。预先定义的关键误放行反例必须全部通过；配对评估报告质量改善、成本及等待时间，计入失败尝试、修复与评审，不能只统计最后一次成功运行。原授权预算仍约束执行，结论不能自动追加额度。有限样本不证明总体零错误；成本上升本身不否决发布，也不能替代质量收益证据。

### Q9：旧任务兼容

用户选择 A：升级后未完成的旧任务可以按原规则收尾，新任务默认使用 0.4.0 新策略。旧任务可以显式迁移；未迁移的结果须标记适用的旧版规则，不得声称满足 0.4.0 的交付要求。保留历史证据与已经发生的外部效果，`update/sync` 不自动改写任务状态。此项沿用显式迁移边界，最终计划须定义可核验的旧任务身份，避免把新任务缺少策略记录当成兼容资格。

### Q10：三仓独立评估规模

用户选择 A：覆盖 lazyzcode（CLI）、openchamber（Web）、zpigeon-ios（iOS），沿用既有环境配方；每仓至少两个未用于调参的任务，每项三次新旧策略配对，至少 18 对、36 次运行，其中包含中断恢复。开发调参集与独立评估集分开；样本与判据在实现前冻结。

## 本轮源码核对新增的基线事项

核对提交 `b8e69de295e3d9d120f54d9c97b794aa30dceb38`，仅源码核对，尚未新增反例实测：

- `core/verify.js` 的 run 回执读取 `goal.contract?.hash`，而 `core/loop.js` 的注册结构写入 `goal.contract.contractHash`；契约回执绑定存在字段不一致，须实测并修正。
- B 交付在 merge SHA CI 为 failed/pending 时也记录意图 done，这是保留已合并事实；`core/queue.js` 的 `deliveryAllDone` 仅按意图 done 判完工，存在把“动作已发生”误当“交付完成”的路径。修复不得回退已合并事实或重复 merge，须补交付结果判定。
- `finishLoop` 尚未统一消费必需执行回执、CI 与独立实现评审；queue 的 done 分支及手动 delivery 路径也须进入统一判定。此项属于 Q2 已确认的旧承诺补齐。
- `judgeReuse` 判断输入适用性而未要求旧执行成功；新放行门必须分别检查“仍适用”和“检查通过”，不得把适用性 true 当作验收通过。

### Q11：旧缺口的版本归属

用户选择 A：前两项纳入 0.3.1 发布收口，先建立失败反例再最小修复，保留既定两棒主线，不新增功能。0.4.0 使用修正后的 0.3.1 基线；后两项纳入 0.4.0 统一放行设计。

### Q12：整体方案与发布门槛确认

用户确认两份完整计划，以及每项任务至少2/3次正确交付、新策略正确交付总数不低于基线、至少一项质量指标改善、关键错误完成为零的发布门槛；成本完整披露但不要求下降。用户原话：“确认。但同样不需要执行。”因此本轮止于文档定案与校验，不启动代码修复、模型实验、外部写入、发布或 Git 提交。
