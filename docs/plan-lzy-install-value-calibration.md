# lzy 安装价值：单用户校准方案

日期：2026-10-05。协议版本：1。状态：**用户已确认目标、约束与分工；交接准备阶段，尚未运行校准。**

本文回答的问题是：对于使用 ZCode 修复真实项目 bug 的开发者，安装 lzy 相比一份简短工作约定，是否值得？协议单源为本文；配套文件为 [ZCode 交接入口](handoffs/zcode-install-value-calibration.md) 与 [记录模板](templates/install-value-calibration-records.md)。

本协议独立于版本发布、策略采纳与旧消融。它不修改决策 #25、#32、#42–#46，不授权默认策略切换，不覆盖历史失败记录。这里新增的是经用户确认的实验安排；将来若依据正式结果更改产品决策，再同步 ADR、decisions.md 与 AGENTS.md。

## 1. 产品问题与已确认决策

首要假设：**lzy 能减少人工盯守，同时保持交付质量，并把额外机器开销控制在可接受范围内。** 这是待验证假设，不能先写进宣传语作为事实。

| 项目 | 已确认规则 |
|---|---|
| 目标优先级 | 减少人工盯守优先；质量与效率仍须检验，不放弃任何一项 |
| 主对照 B | 原生 ZCode＋简短、合理的工作约定，保留正常项目说明及工具能力 |
| 候选 L | 同等宿主条件下，按拟提供给用户的真实方式使用完整 lzy |
| 正式验证目标 | 人工主动时间至少减少 30%；质量不下降；产品模型费用最多增加 25%；端到端耗时最多增加 50% |
| 严重错误 | 一例经独立复核确认的严重错误交付，即判该候选本轮不通过；节省时间不能抵消 |
| 首轮目的 | 校准实验，不认证产品收益，不以六题证明总体错误率为零 |
| 参与者 | 用户本人；外部开发者招募不作为本轮阻塞项 |
| 任务 | lzy 之外真实项目的六个未解决 bug；用户尚不知道修法；预计需要跨文件定位或修改 |
| 分配 | 预先按可见难度匹配三对，每对随机分给 B、L 各一题；每人不重复做同一个 bug |
| 终点 | 本地可验收修复：可检查的修复、相关验证、清楚的结果与限制说明，用户实际验收接收 |
| 模型预算 | 历史同口径 200 积分：任务 150，独立实验验收 30，环境冒烟与计量校准 20 |
| 后续方向 | 纯原生 ZCode 辅助对照、功能开发、重构或迁移分别扩展，不用 bug 成绩替其他类别背书 |
| 产品取舍 | 正式验证及必要消融若显示精简组合更有价值，愿意以精简组合为默认形态；不由本次校准自动改产品 |

首次安装、配置、学习的人工时间与模型成本另列，以后计算多少个任务能收回投入；不得藏起这些成本，也不将每次为实验重建隔离环境的负担当作日常安装成本。

## 2. 证据起点与边界

- [0.4.0 评估](reviews/v040-policy-evaluation.md) 是旧、新两版 lzy 的比较，不是本协议的安装价值比较。原始批次各 18 次，正确交付各 12 次，goal 完成旧 18、新 0；已记录积分 170.83 与 98.43，七次缺失全为超时。不能据此宣称质量提升或完整总成本下降。
- 历史可计量单次中位约 7.6–9.9 分、最高约 19.1 分，仅用于粗设预算。任务、模型与评审方式可能不同，200 分不保证六题完成。
- [b3 消融](reviews/2026-09-21-v021-ablation-b3-report.md) 提供局部机制信号，每组合一次不足以量化普遍贡献；旧仪器污染不能被新计划掩盖。
- [既有 0.5.0 建议](plan-v050-closure-and-evaluation.md) 的版本对照和本协议回答不同问题。现有 `scripts/evaluation/run-pairs.mjs` 的 `qualityGate` 要求每题多次运行及质量严格改善，**不能用它直接裁决本轮不同任务匹配、每题一次的校准**。
- 本次编写时仓库 HEAD 为 `9171d240712535d71e4bfc58e585fea031ccc031`，HEAD tree 为 `9d2d46cbe2dca3722324b207220973617c45b572`，包元数据为 0.4.1。工作树已有 cost/doctor/review、相关测试及 0.5.0 建议等未提交内容。它们不是已冻结候选；接手者必须重新盘点、保留并明确取舍，不能把工作树等同发布版。

## 3. 分工与授权边界

| 角色 | 责任 | 独立性边界 |
|---|---|---|
| 方案维护者 | 固化协议、记录偏离、维护交接材料 | 不能看到结果后改旧门槛使其过关 |
| ZCode 协调会话 | 环境盘点、仪器准备、冻结批次、组织运行与收账 | 不额外帮某一组解题；协调者提供的任务级帮助全部计入并披露 |
| 两臂执行会话 | 各自取得需求，在隔离副本履行任务 | 每题新会话；不共享答案、转录、隐藏判据或另一个实验臂的经验 |
| 用户 | 正常操作、处理请求、计时、验收本地交付 | 人的主动时间必须来自真实参与，不能由模型估算替代 |
| 独立验收/复核会话 | 在冻结产物上运行独立检查、复核严重错误与记录完整性 | 首轮尽量隐藏实验臂及执行者自评；不实现被测修复，不以自己的赞同替代功能检查 |

本次授权首先支持方案交接、只读盘点与可逆的实验准备；不授权发布、推送、合并、线上部署、破坏性操作或改写用户 `config.json`。隔离副本内若候选流程需要 Git 提交，应把该动作列入任务启动卡并取得对应授权；不能从“做实验”推导任意 Git 权限，也不能用消融授权门来省掉真实用户操作。

不招募、不联系第三方。用户的实际参与时段、仓库权限、原生审批要求属于真实启动条件。所需信息能从本机查到就先查；确实缺少的授权或参与安排应合并成一份具体启动卡，避免反复询问已拍板事项。

## 4. 开跑条件与冻结清单

以下项目在第一题开始前均须有明确记录；“待定”“稍后补”不算满足。可以先进行不产生新模型消耗的只读检查、文件准备和本地诊断。

| 必须冻结的项目 | 方法与退出条件 |
|---|---|
| 模型与计价 | 记录实际 provider、主模型、产品评审子模型、计价单位与来源；确认 200 分与当前实际消耗同口径。无法映射则停止付费派发，重新提交可审核预算，不猜人民币汇率 |
| 候选身份 | 指定发布包或明确候选包、内容哈希、源提交与补丁/未跟踪文件清单。未提交改动只能显式纳入或排除，不暗中夹带 |
| 启动方式 | 主任务使用真实 ZCode 用户交互表面；配对两臂使用相同宿主交互方式。headless 可用于仪器冒烟，不冒充人的盯守实验 |
| 单题绝对时限 | 冒烟后为每个匹配对冻结共同墙钟截止；记录依据与用户参与窗口。相对＋50%不等于单题超时配置；时限不因看见某臂进度而延长 |
| 介入规则 | 冻结检查进度的节奏、请求回应方式、静默停滞判据、验收失败后的反馈和恢复规则，见 §7 |
| 工程准备预算 | 200 分包含既定实验三账，不包含另行开发工具的付费模型消耗。若需付费修仪器，先列最小修复清单、独立额度与验收，再取得额度授权；不能挪实验钱或暗中用别的模型代付 |
| 六题与环境 | 来源、原始基点、正常项目说明、匹配理由、可复现环境、公开验收条件、隐藏检查版本及保管角色全部登记 |
| 隔离与权限 | 确认没有被全局/祖先目录的 lzy 指令污染；各题具有相同类型的工具与外部动作权限；用户数据受保护 |
| 顺序与记录工具 | 冻结 seed、分配、实际执行顺序、计时工具、会话归属及费用去重办法；完成正反仪器冒烟 |

冻结后任何模型、候选、提示词、验收或计量语义变化均追加偏离记录。不得在同一批中悄悄换候选再混算；已消耗保留，必要时本批以未完成结束。用于改进产品或仪器的任务随后归开发集。

## 5. 两臂配置与任务取样

### 5.1 公平的低成本替代方案

B 臂共同工作约定草案如下；环境校准允许澄清一次，最终文本及哈希须在分配前冻结。L 臂取得相同需求和共同约定，再按实际产品入口使用 lzy。

> 请定位并修复下述 bug，遵守本项目说明和已授权范围。必要时先简要说明计划，完成实现后运行与改动相关的验证，检查回归风险。如有阻塞，明确缺少什么；如未完成或验证失败，如实说明。交付可在本地验收的修复，列出验证结果和剩余限制。

B 臂不加载 lzy 插件、技能、钩子、全局纪律或残留状态；也不人为削弱正常 ZCode 工具。L 臂保留真实审批和产品内评审，禁止用 `LZY_ABLATE_*` 开关把摩擦移出测量。执行会话不需要知道收益门槛，避免为指标优化行为。

隔离工作区应位于 lzy 仓库及其指令继承范围之外；存放在本仓 `artifacts/` 的副本仍可能继承本仓 AGENTS.md，不能仅因“是副本”就声称隔离。用真实加载清单/会话元数据核对插件、hooks、skills、全局和祖先指令、模型与权限。实验用设置通过宿主支持的隔离机制建立；不手改用户配置，也不导出认证秘密。

### 5.2 取样与分配

1. 只读收集真实待办及复现线索。保存所有候选和纳入/排除理由，禁止只留下“看起来 lzy 会赢”的题。
2. 纳入：外部于 lzy 的真实项目、问题尚未解决、用户不知修法、有可复现症状与本地验收路径、预计涉及跨文件工作、环境可在额度内准备。
3. 排除：已被本次实现/调参会话解决或看过答案、需要生产破坏/上线才可验收、缺必要权限、环境无法复现。环境不支持是适用范围限制，需保留在筛选账。
4. 在分组前仅凭公开信息按项目熟悉度、技术栈、环境成本、预计定位难度、验收复杂度配成三对。不能为证实“多文件”而先解题；最后只改一文件的任务仍保留，不事后剔除。
5. 由独立准备会话编制验收，公开用户应知道的功能要求；隐藏的是具体检查实现和负例，不是偷偷新增需求。准备会话不把可能的修法交给参与者或执行会话。
6. 用可重放伪随机过程分配：每对恰一题 B、一题 L；随机化对内运行顺序并保存 seed/算法/输出，避免全做 B 再全做 L。六题串行，不让同时运行的工作抢占同一人的注意力。
7. 找不足六个合格任务就报告短缺，等待新真实待办或由用户调整范围；不拿历史已解题、注入题或随意功能需求补足。

## 6. 预算、计量与中断

| 账 | 额度 | 计入内容 |
|---|---:|---|
| 产品任务账 | 150 分，六题各 25 分 | 执行、产品内计划/代码/QA 评审、失败、格式重试、恢复、所有子会话；每题从第一次尝试累计，不因 reset 或重启清零 |
| 外部实验验收账 | 30 分 | 实验专用隐藏检查准备、独立判定及争议复核所用模型；同一次评审不得在两账重复算 |
| 冒烟与计量账 | 20 分 | 环境和加载核验所需模型、正常结束与受控中断后的计量校准 |
| 独立工程准备账 | 未授权额度 | 另行开发、修复评测工具的付费模型消耗；缺明确额度不得开始这种付费工作 |

不自动追加，不跨账挪用，不把别题剩余额度转给跑得慢的一臂。纯本地测试/脚本不消耗模型积分，但仍记录耗时和环境成本。六题的用户安装学习与项目准备另记；其付费模型请求也必须在启动前指定已授权账，不能出现表外会话。

以会话标识、请求/用量记录与计价身份关联全部消耗，保留原始 tokens、积分、provider/model、父子会话关系和来源。所有启动的会话都必须可解释；幂等去重，重试或恢复不会漏算/双算。汇总应能从原始记录重建。

`core/queue.js`、`core/cost.js`、`core/review.js` 等现有功能是可复用候选，不是计量正确性的证明；尤其要核对主执行与产品评审子账是否完整合并。不能仅看一个预算视图就认为已含全部评审。

**近似限制语义：**在每次可计量请求/段结束后检查累计额，并拒绝后续派发。启动前核对已知消耗和未决请求；小预算下不并行启动付费子会话。达到单题或任一对应账上限就停止该范围的新调用。在途请求可能造成超额，必须如实记录；200 分是停止派发阈值，不宣称绝对账单硬顶。

查不到账、未计价、provider 漂移、请求仍未结算时，不记零，不继续开新付费会话赌它便宜。保存已知下界、未知记录及现场；优先本地只读对账。仪器恢复以前成本门不可判。记录审计不能因费用用尽而由执行者自签通过；所需复核无法完成就保留未判定。

## 7. 人工时间、结束点与失败

### 7.1 要测的时间

- `H`：真实人的主动时间。阅读任务和进度、写提示、回答问题、审批、诊断阻塞、救场、处理 lzy 操作、阅读交付说明、运行/观察用户验收均计入。使用开始/结束事件记录区间；不靠回忆补一个精确数字。漏记要标未知，不能用 token 数或代理估计代替。
- `W`：从干净可用环境中用户开始该任务，到用户接收本地修复的日历耗时。另记执行者首次提供可验收候选的时刻，以区分产物准备与用户验收等待。产品内评审和收尾计入；实验独立盲审发生在冻结产物后，单独计时。
- `C`：对应题全部产品模型费用，包括产品内评审和所有尝试。独立实验准备/判定与安装学习成本另外列示；报告同时给出整轮所有账的总费用，不把评测开销包装成用户日常成本或反向隐藏它。
- 首次安装/学习、实验记录操作、独立审计分别记账。人的实际验收属于 H；为研究填写额外表格属于实验开销。两者不能重复统计。若为了操作 lzy 必须填写文书，属于产品负担，计入 H。

### 7.2 相同的介入规则

启动前固定两组相同的用户可用时段和检查节奏。正常回答明确的需求/权限问题；停滞达到预设间隔后可作一次中性状态询问，后续恢复按同一规则进行。具体间隔由冒烟和用户工作节奏确定并写入 manifest，不在看见某组表现后改变。

用户可为避免真实损失随时介入；所有介入记录原因、内容、主动秒数与影响。不要刻意忍住基线求助，也不要为候选额外提供解题提示。若用户直接修改代码或协调者代修，记录人/代理贡献；该题保留并标为辅助交付，不能宣称模型独立完成。

每次向用户声称完成或提交验收，都先保存该时刻的源码/补丁快照及哈希、原话、时间和公开验收结果；同时保留未提交内容，不能只记 HEAD。快照只追加，不被后续修复覆盖。本地保全不要求每次新增付费评审。

用户验收不通过且不存在疑似严重错误时，在原单题预算和绝对时限内可以把公开失败现象反馈给原会话修复，两组规则相同，全部返工计时计费。出现疑似严重错误则先保全并暂停，由独立会话复核对应历史快照；后续修复不能撤销已经确认的严重错误。外部隐藏判定检查终端快照及必要的历史交付快照，具体隐藏断言不反馈给执行者，不提供反复试答案的通道。

### 7.3 正确性与完成状态分开

每题都报告：正确且用户接收、正确但未接收/未收尾、错误却宣称完成、错误且未完成；未知检查另列，不能硬塞进正确/错误格。lzy 内部 goal 状态单列，不是跨臂正确性权威。保存声称完成、候选就绪、用户接收与终止的各个时刻。

严重错误指：关键验收未满足却向用户宣布完成、新增关键功能回归、越权破坏性操作。候选出现疑似严重错误即保存现场、暂停后续实验派发，先独立复核；确认后候选本轮不通过。基线同样检查与报告，不能因基线也出错豁免候选。未确认的疑点标为未判定。

普通任务失败、额度耗尽、超时、用户退出、仪器故障分别记录。已分配任务不从报告消失；未开始也列原因。失败任务的 W 是截至停止时的观测下界/截尾，**不是更快的成功交付**。未知费用不当零；不能靠提前放弃获得省人、省时、省钱结论。

## 8. 验收与仪器校准

验收基于独立的 bug 复现、冻结功能要求、相关回归和真实表面检查；不能只跑代理自己刚写的测试，也不能以评测 agent 的“PASS”代替功能行为。

开跑前用非正式题检查：

1. 已知有缺陷的样本确实判失败，已知正确样本确实判通过；环境错误、超时、判定器崩溃单列为未知/仪器失败。
2. 短会话正常结束以及受控中断后，所有子会话和用量能归账；缺失可识别并阻止下一次付费派发。
3. 人工计时至少走一次完整开始/暂停/继续/结束与重叠去重；无用户事件时不能生成“零人工”的成功报告。
4. 基线加载核验、候选插件启用、实际模型、权限、路径和副本身份可回读；不能仅验证包已经安装。
5. 一道验收失败后反馈公开症状并恢复的演练，两组规则可执行；不修改正式六题来测试仪器。

如果使用模型作辅助评判，用户对已知正反样本作人工标注，复核模型是否错放、错拒或漏判；保存不一致及处理。小规模校准只证明本组检查可用，不宣称评测 agent 已普遍对齐人类。无法可靠判定的要求不纳入本轮正式题。

## 9. 分阶段执行与验收

依赖：P0 → P1 → P2 → P3 → P4。准备中的独立只读盘点可以并行，真实用户试验串行。

| 阶段 | 工作与产物 | 退出条件 |
|---|---|---|
| P0 只读盘点 | 仓库/宿主/候选/现有工具清单；任务候选列表；现存改动保留记录；工程缺口与准备预算建议 | 能指出具体阻塞及最小修复；不把未知当可用，不提前解题 |

仪器修复后的重试仍保留旧尝试与成本，不能让任务第一次接触重新发生。若用户已见解法，后续运行只算开发演练；没有原始用户计时就不能补成正式人工收益样本。

## 10. 分析与校准停止条件

本轮样本是**三对不同任务**，不是同一道题的重复配对；随机化只能减轻选择偏差，不能消除任务难度差异。用户知道自己在哪一臂，熟练度与期望效应也须披露。

报告逐题原始 H/W/C、验收状态、介入原因、逐对差值；再给完整分配口径的描述汇总。可展示 B/L 的均值与比值，但基线为零、缺失、未完成或任务不平衡时写明不可解释的原因。只比较成功题会有幸存者偏差；即使另列“两题均成功”的差值，也不得用它替换全批结果。

`1 - H_L/H_B`、`C_L/C_B - 1`、`W_L/W_B - 1` 仅在同口径、数据完整且结果状态可比时作为描述数。不能把未完成 W 当完整耗时混入提速结论；缺失成本只能报已知下界。六题不作显著性、总体非劣效、普遍－30%或“零风险”宣称。

校准结案必须属于以下之一，并说明每个任务与预算的去向：

- **仪器不合格**：费用、时间、隔离或验收不可靠；先修仪器，无收益结论。
- **校准未完成**：预算/参与/环境等原因不足六题；已有记录保留，无产品通过结论。
- **测量可用、收益未定**：六题记录和独立验收可用；可以提出方向性观察及正式实验设计输入。
- **候选因严重错误不通过**：保留已确认反例，先处理该问题；这不等于已证明整个产品永久无价值。

正式验证另建新任务集，基于本轮测得的波动、成功率、绝对人工节省和费用规划样本量/总预算，预先确定统计口径与可接受的不确定性。不能只因为六题“看起来差不多”就机械乘一个倍数宣称样本量足够。正式通过须同时满足质量和资源约束，不能换目标消化负结果。

如正式结果有收益，再围绕疑似贡献做部件消融；贡献依赖组合，不简单相加。若简化组合更好，形成有证据的默认调整提案，按现行决策与发布流程落地。功能开发、重构/迁移及其他用户分别验证；继续保留这些方向，不提前承诺通用收益。
