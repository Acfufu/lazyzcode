# lzy 状态存储演进：先修账务，再迁局部 SQLite

日期：2026-10-11（同日经独立评估复核并补强，修订记录见 §9）。状态：规划落盘，尚未实施；P0 启动已获授权，前置＝评审沙盒工作集（ADR-0038）先收口入库、P0 从干净树起步。本次修订只补强计划文本，不启动账务修复、数据库迁移、真实模型运行或发布。不指定版本号，不改变现行 ADR 与默认行为。

## 1. 目标、范围与停止条件

先使消费记录、计量完整性和事件身份可信，再把工作区内的队列、派发与预算账迁到一个 SQLite 数据库。第一阶段的收益目标是减少跨文件写入的中间状态、提供可靠去重和可重复恢复；不承诺未经测量的性能提升。

执行顺序：**P0 修账务 → P1 冻结边界并做隔离试点 → P2 实现事务与恢复 → P3 显式迁移与切换 → P4 真实 CLI 验证与交接**。各批独立验收；P0 可以独立交付，P1 通过后才进入生产实现。切换路径和钩子兼容性未满足时不得启用 DB 权威模式。

最终停止条件：账务反例通过回归验证；队列占用与结算分别原子提交；异常后消费和未决占用不丢失；迁移可核对、可重入；授权钩子读取权威数据；支持的平台与最低运行时完成验证。达到条件后停止扩围，观察实际使用再决定是否迁 goal/DAG/runtime。

首批边界：

| 对象 | 本计划处理方式 |
| --- | --- |
| 工作区 queue、dispatch、budget ledger/settings | 迁入同一个工作区 SQLite；建议路径 `.lazyzcode/state.sqlite`，P1 冻结 |
| 独立 review 对工作区预算账的读写 | 同步适配，避免 queue 与 review 各写一份权威账 |
| goal、DAG、attempt、runtime、授权、交付意图 | 保留当前文件与语义；处理与新 DB 的协调和恢复，不在本批迁移 |
| 证据、转录、候选快照等大文件 | 保留文件产物；必要时只在 DB 保存身份与引用 |
| ZCode 自己的 `db.sqlite` | 仍由宿主写入，lzy 查询；不迁移、不修改宿主 schema |
| 全局 `lzy-usage/*.jsonl` | 修复身份与完整性，继续作为跨项目观测面；不承诺与工作区 DB 跨库原子提交 |

SQLite 不改变 OS 沙盒边界，不等于供应商余额，也不能把逐段消费检测变成严格积分硬切。模型请求、进程、Git 与远端交付不属于数据库事务。

## 2. 当前依据与依赖

当前 lzy 自有状态采用带版本、形状校验或校验和的 JSON，配合临时文件原子替换与目录锁；有单文件保护，没有跨 queue/dispatch/ledger 的统一事务。

- [queue](../core/queue.js)：派发先落 dispatch 占用，再写 queue 的 running；结算涉及多次消费追加与状态写入。`appendLedgerEntry` 目前扫描去重并整本重写，恢复确认依赖 ledger seq。
- [review](../core/review.js)：独立评审直接读写工作区预算账，必须纳入存储适配。
- [cost](../core/cost.js)、[补账脚本](../scripts/harvest-sandbox-usage.mjs)：全局观测与补账身份、完整性需要先修。
- [trigger](../plugin/hooks/trigger.js)：钩子直接读 queue.json 解析交付批准，不能在 DB 切换后继续信任可能过期的 JSON 投影。
- [loop](../core/loop.js)、[runtime](../core/runtime.js)：仍存在 JSON 生命周期与租约协调，局部 DB 不覆盖这些跨存储转换。
- [既有 migrate](../core/migrate.js)：承担特定版本的目标迁移，不视为现成的通用 DB 迁移框架。

缺陷依据为本地 [沙盒与预算评估报告](../artifacts/sandbox-budget-evaluation-2026-10-11/report.md)，F1–F5 来自历史探针。本地 artifacts 不随仓库发布，核心反例在 P0 表中保留。实施时重新复现，不能把历史报告当作当前源码已验证结果。此前独立评审沙盒 A/B 改动不属于本计划，保留其工作集与证据。

与 [完整产品价值计划](plan-native-product-value.md) 的全链路计量要求重叠；复用同一账务修复与事件身份，不建立第二套成本口径。SQLite 迁移不作为该实验计划自动增加的前置条件。

## 3. P0：先修账务语义

依赖（2026-10-11 拍板）：评审沙盒工作集先收口入库，P0 从干净树起步——红绿证据与并行 WIP 混树会互相污染（先例：外来 untracked 文件拦 finish）；实施启动后仍须重新检查现行代码。每个已复现缺陷先保存失败检查，再做最小修复。

| 顺序 | 工作 | 验收反例 |
| --- | --- | --- |
| P0.1：F1/F2 | 分离已知消费、计量完整性与计价覆盖；超额只作解释或派生值，不能再计入实际消费 | 部分缺失/未计价仍保留已知 tokens 与积分，持久标未知；受积分帽约束的后续派发/评审按既定策略停止并可核对恢复；实耗 60、帽 50 显示消费 60、超额 10；多段与重复结算不多扣 |
| P0.2：F3/F4 | 项目、运行实例与源事件身份分开；运行实例创建时持久分配，不能用金额、tokens 总数或可复用 runId 判重 | 两项目同名 run 不串账；累计 50→150→250，补账最终 250，重放仍 250；清理重建后的等额新运行不被旧记录吞掉 |
| P0.3：F5 | 观测结果携带 corrupt/unreadable/missing/pending 诊断；追加失败可见；保留可重放来源 | 坏行、不可读、追加失败不显示完整 ok；恢复只记一次；源账与汇总未确认保全前不删除用量来源 |

事件身份必须依据宿主可提供的真实字段确定；源字段不足时先保留明确歧义，不能编造唯一身份或用数值指纹代替。对历史不确定记录保留来源和缺口，不通过迁移将未知改写成零或完整。

交付：账务契约、最小修复、红绿验证与真实 CLI 读面记录。P0 不引入 SQLite，收益独立兑现。

## 4. P1：冻结局部 DB 边界并做隔离试点

依赖：P0 验收。先形成存储契约，后定 schema；不为了通用性加入 ORM、服务进程或额外依赖。

候选实体为 queue items、dispatches、dispatch segments、budget events、budget settings 与 schema/backend metadata。事件金额、tokens、计量状态、计价依据和来源分开表达。数据库保留现行授权绑定 `(slug, contractHash)`、seq/ack 恢复确认、未知占用与 reset 不清预算语义；不另铸替代授权身份。

明确需要一起接入的调用面：queue 读写与恢复、review 预算读写、status/doctor 读面、钩子交付批准、相关测试和脚本。保留业务入口，由存储层集中实现 DB 访问；不能只给旧 JSON 的 load/save 外面套 DB 而仍逐文件提交。观察面契约（#46）不因换后端破坏：status/doctor `--json` 的 schemaVersion 只增不改，backend 切换不得改变既有字段形状，只允许新增字段。

在隔离目录验证唯一事件约束、占用事务、结算事务、并发冲突和崩溃恢复。冻结事务内操作、锁顺序、忙等待/超时处理、连接关闭、备份与 WAL 处理方式；不得把网络请求或执行等待放进事务。

运行时检查包括 CLI 与宿主实际启动钩子的 Node，不能只看开发终端。当前 package 声明 `node >=22`；若用内置 `node:sqlite`，须核实最低可用版本并同步 engines、doctor 和安装说明。已知事实（2026-10-11 核）：`node:sqlite` 于 22.5.0 引入且需 `--experimental-sqlite` 旗标，22.13.0 起去旗标（仍标 experimental），22.0–22.4 无此模块，另有部分 22.5.0 构建缺该模块的报告——现行 `>=22` 实际 admit 的 22.0–22.12 均不可直接用。冻结最低运行时的实质选项＝engines 提至 ≥22.13.0（收窄用户基数）、运行时探测降级明确拒启、或等稳定代际；属难逆取舍，定案时按仓库规则立 ADR。参考 [Node SQLite 文档](https://nodejs.org/api/sqlite.html) 与 [SQLite WAL 文档](https://www.sqlite.org/wal.html)，只使用选定最低版本具备的 API。工作区在不支持 WAL 的文件系统等环境下须明确拒绝或采用已验证策略。

验收门：CLI 与钩子能读同一权威存储；关键事务试点通过；锁与恢复契约可执行；迁移/备份策略明确。任一不满足则停在试点，不更改生产默认。

交付：范围、schema 与存储契约、能力矩阵、试点及故障证据。进入实现时，涉及难逆且有真实取舍的定案按仓库规则新增 ADR，并同步 decisions/AGENTS；本文不预先将候选设计列为现行决策。

## 5. P2：实现事务及外部动作恢复

依赖：P1 验收，迁移和切换方案已可实施。实现先在隔离工作区运行，P3 前不接管用户现有状态。

两处核心事务：

1. **派发占用**：在协调规则下复核就绪、授权与预算 → 登记派发意图及保守占用 → 条目置 running → 一次提交。
2. **结算**：采集用量并保留完整性 → 唯一键追加预算事件 → 更新 dispatch 结算状态与 queue 应达状态 → 一次提交。保留现行失败后回 ready 等恢复路径，不要求每次结算都将队列项置为终态。采集外部用量在事务外完成，提交前按既定版本/身份规则复核。

事务提交后才启动外部进程。启动成功但尚未记录 PID/session 的窗口仍可能崩溃，必须通过持久意图、运行身份和存活核对恢复；无法判断时保留未决占用，不能盲目重派或自动当零。

goal 注册、计划采纳、start/reset、lease/fencing 与交付仍在事务外。保留适用的协调锁，固定锁与数据库事务获取顺序；授权/目标漂移仍需复核，不能声称局部表原子化覆盖整个目标生命周期。沿用现行恢复语义，不借迁移扩展默认并发派发能力。

review 的预算追加与汇总调用接到同一存储层；全局观测追加采用可重放来源并暴露 pending，不追求工作区 DB 与全局 JSONL 的分布式事务。

验收：重复消费事件只生效一次；并发竞争不重复认领；提交前后中断不产生半套队列/派发/预算状态；未知消耗和在途占用持续可见；已有授权、租约、交付门与 reset 语义不弱化。

## 6. P3：显式迁移与一次权威切换

依赖：P2 验收；CLI 与插件的新旧格式兼容策略通过验证。`update/sync` 不自动迁移。

步骤：

1. 确认无活跃派发、评审入账或其他写入者；取得迁移协调锁并冻结写入。
2. 备份相关旧状态，登记迁移 journal、源指纹和恢复信息（journal/提交点协议形态沿用 ADR-0029 迁移机器先例）。DB 备份按选定 SQLite 策略处理，不复制单独主文件冒充 WAL 一致快照。
3. 导入临时 DB，核旧文件版本、形状/校验和、关联身份和事件唯一性；保留历史 seq、ack、限额、授权引用、已知消费及未知状态。
4. 逐项语义对账并检查 DB 完整性；发现重复身份冲突、损坏或不可解释差额则停，不静默合并或修正历史。
5. 安装核实支持新格式的 CLI/插件后，按已验证的 journal 与提交点协议切换 backend 标记。文件标记与 DB 不具备天然跨资源事务，必须覆盖中断重入。
6. 切换后 DB 是唯一权威；旧 JSON 保留只作备份/导出。DB 缺失、损坏或读取失败不能回落到旧 JSON 继续派发或批准。

钩子必须读取 DB 或权威读接口；过期 JSON 投影不得生成批准记录。读取异常给出诊断，不让钩子失败演变为授权放行。

不能假定旧 CLI 认识新 backend 标记。切换前处理 CLI/插件版本冲突；切换后检测旧状态误写并阻断新版继续派发，提示核对，不能承诺同一用户权限下可强制阻止任意旧二进制写文件。

回退边界：切换前可取消并保留旧权威；切换后没有新写入且经过核对可恢复；已有新写入则需停写、备份 DB、反向导出并完整对账。未实现且未验证反向导出时明确不支持自动回退，不能恢复旧备份丢掉新账。

## 7. P4：验证、证据与交接

通过真实 CLI 执行以下场景，模型/进程行为优先用本地测试引擎，无需付费调用：

- 事务提交前后中断、进程启动后未回执、结算中断、重复 reconcile 与重复补账。
- 并发 dispatch、review 与 queue 入账竞争、锁等待/超时，核无重复认领与漏账。
- 迁移各步骤中断重入、源数据漂移、导入损坏/身份冲突、backend 标记与 DB 不一致。
- 钩子正确批准、DB 不可读时不生成批准、CLI/插件版本冲突及旧 JSON 误写。DB 不可读分支的验收必须走钩子 stdin 驱动的契约测试——外层 catch 走 failOpen，CLI 读面断言测不出该分支（hook-failopen 先例）。
- reset 后累计预算与恢复确认保留，契约绑定、未知状态、现行 lease/fencing 和交付恢复保持。
- 导出与备份恢复；若提供反向迁移则验证切换后新增账完整保留。
- 支持平台及最低 Node 版本的真实 CLI/钩子读写；平台限制和未运行检查明确记录。

基线可参考 [budget ledger](../test/budget-ledger.contract.test.js)、[dispatch recovery](../test/dispatch-recovery.contract.test.js)、[queue metering](../test/queue-metering.contract.test.js)、[review runtime](../test/review-runtime.contract.test.js)；原有直接写 JSON 的夹具按后端重建，不通过删除旧行为断言获得通过。

记录源码状态、精确命令、检查结果与故障日志；针对受影响范围跑检查，再跑适用全量测试。独立架构终审核验最终 diff 和证据，修复实质阻塞后交接；实现变化时刷新受影响证据。

性能比较只作为辅助：在相同数据量、机器和操作下测追加、查询、锁等待与恢复步骤；当前小账本不能证明性能瓶颈，未测不宣称提速。SQLite WAL 仍是单写者，不以迁移为由扩大调度并发。

## 8. 交付顺序与当前待定项

| 批次 | 主要收益 | 出口 |
| --- | --- | --- |
| P0 | 账目可信度立即改善 | 独立修复、反例红绿证据 |
| P1 | 降低迁移风险 | 存储契约与隔离试点；不可行则停止 DB 切换 |
| P2 | 建立原子占用/结算和恢复能力 | 隔离工作区实现通过；生产收益尚未兑现 |
| P3 | DB 接管后兑现局部一致性与增量写入 | 显式导入、核对、单权威切换 |
| P4 | 证明恢复与兼容行为 | 源码绑定证据、限制说明、独立审查与交接 |

P1 冻结项：真实源事件身份、schema 与数值表示、最低运行时、钩子权威读路径、锁顺序、busy 策略、备份/WAL 支持环境、迁移提交点、版本冲突与回退能力。这里不预先虚构已完成设计。

首次交付后观察实际队列使用、历史查询与崩溃恢复成本；只有常态使用或实测显示 goal/DAG/runtime 的存储成为主要问题，才另立扩围计划。全量迁移、远程 DB、跨项目统一写库和新调度器不属于本计划。

当前五批均未启动。本文仅将已讨论顺序与审查边界保存为后续实施依据。
