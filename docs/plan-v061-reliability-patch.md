# 0.6.1 审计后的可靠性补丁实施计划

日期：2026-10-25。状态：**用户已授权实施；R0 生命周期门未通过，R3 已本地实现并验证，整体补丁部分完成。** 具体证据与未通过项见[执行记录](reports/reliability-patch-2026-10-25.md)。本文不指定下一版本号，不启动模型实验、提交、推送或发布；各阶段目标与验收门仍按原定范围执行。

## 1. 目标与已确认范围

先交付一个独立可靠性补丁：修复无人值守运行的进程回收边界、全局评审用量账本的并发重复追加、跨项目失败回执覆盖；同批处理 D2、D3 和双语发布文案漂移。原生 ZCode 对照的产品价值 M0 留在[另一份计划](plan-native-product-value.md)，本补丁不启动该实验，也不据此宣称质量提升或成本下降。

| 已确认事项 | 实施约束 |
| --- | --- |
| 修复优先 | 可靠性补丁独立收束，再交接产品价值验证 |
| 清理能力是前置条件 | 无法证明具备所需回收能力时，在派发前具名拒绝无人值守执行；不能运行后只给警告 |
| 覆盖完整托管链路 | 主会话、workers、嵌套独立评审及其托管后代均纳入；远端已受理请求不承诺可撤销 |
| 三平台完成门 | macOS、Linux、Windows 的必需行为均须实测通过；把 Windows 全部禁用不能算补丁完成 |
| 生命周期按整次 drive 划分 | 后台进程允许跨分段复用；整次 drive 完成、预算停止、取消或失败收束时回收，保留工作文件与普通日志 |
| 控制器被强杀 | SIGKILL／平台等价强杀后须可诊断、可恢复；不承诺瞬间清完。下一次启动先处理遗留，确认清理完成前不派发新任务 |
| 账本历史 | 保留 append-only 历史，不重写或自动清洗旧消费；不把全局 JSONL 迁进工作区 SQLite |
| 验证方式 | 使用隔离目录、真实本地进程与文件系统、三平台运行证据；不调用付费模型 |

用户已授权按阶段执行常规工程工作；只有实证表明无法满足以上契约、需要改变依赖或平台支持边界时，才提出具体取舍。

## 3. 设计边界与不变量

### 3.1 运行拥有进程，分段只借用运行上下文

新增职责限定为 lzy 已发起执行的生命周期管理，不扩展为通用调度器、模型路由或宿主工作流替代品。保留 [ADR-0036](adr/0036-host-orchestration-base.md) 的宿主编排边界、[ADR-0020](adr/0020-runtime-kernel.md) 的 lease／fencing 语义，以及 [ADR-0039](adr/0039-sqlite-store-boundary.md) 的存储分界。

1. **一个 drive 一个运行身份。** 身份不能仅用 PID、slug 或可复用的分段编号。运行上下文包含唯一 runId、工作区、现行 fence、绝对截止时间、控制器身份及托管进程集合。新增字段名、磁盘位置和版本在 R0 冻结。
2. **先建立可恢复的归属，再允许执行。** 解决“子进程已启动但登记未落盘”窗口；至少持久化启动意图，并由平台机制确保未完成归属的进程不会脱管运行。普通 spawn 后补写 PID 不能视为已解决。
3. **分段结束不等于运行结束。** 引擎退出、stdio 关闭和后台进程存活分别处理；无需等待后台持有的管道关闭才能进入下一段。后台服务不得因此丢失归属，下一段仍可复用。
4. **同一截止时间向下传递。** worker、独立评审、评审重试使用父级剩余额度与自身上限中的较小值；不得为新分段、重试或子进程重开父级墙钟。到期立即停止新派发，并进入有界回收。
5. **统一收束入口。** 正常结束、预算耗尽、SIGINT／SIGTERM／平台取消、异常、lease 心跳失效均停止后续派发，并触发同一可重入清理流程。清理宽限另行记录，不能宣称宽限内仍在继续执行符合预算。
6. **嵌套评审显式接入。** 独立评审已有自己的进程组、代理及凭据清理，不能假设杀主进程组会带走它。继承上下文须经运行记录和归属校验，不能把任意环境变量当权威；独立 CLI 评审保留自有生命周期。
7. **清理结果不能伪装为任务完成。** 目标完成状态与运行清理状态分别表达；未能确认停止须保留 pending、具名诊断和失败结果。已完成目标不因清理失败被重新派发，清理失败也不能被目标 done 吞掉。

### 3.2 强杀恢复与平台能力

建议在独立生命周期模块中封装平台适配与归属记录；`core/runtime.js` 继续负责同步状态和 lease，不把 spawn、长等待塞进其临界区。新模块路径只是实施建议，R0 后按最小改动确定。

- 记录须跨控制器崩溃存活，并避免被普通 `loop reset`、临时文件清扫或过期租约回收误删。租约释放／过期不代表子进程已清理；启动门必须独立检查待清理状态。
- 回收依据使用平台可核验的进程身份／归属句柄；PID、进程名或命令字符串不足以授权杀进程。身份不确定、PID 复用、记录损坏时具名阻塞，不误杀其他运行或用户进程。
- 接管恢复先互斥认领恢复权，再核验旧控制器是否仍活跃；不得同时清理一个活跃运行。清理完成后才能移除阻塞标记，再按现有契约决定是否发起新任务；恢复本身不重跑已完成段。
- 恢复要覆盖嵌套评审的进程组及 [review-sandbox](../core/review-sandbox.js) 的临时凭据／代理清理。`sandbox-cleanup.json` 现有文件清理回执不能代替进程死亡证明；敏感临时材料按现行规则删除，普通输出和证据保留。
- 三平台分别证明所用机制的归属、跨段存活、正常／异常回收与控制器强杀后恢复行为。POSIX 单进程组不足以自动包含另起会话的后代；若真实宿主路径会脱离管理，必须纳入机制或在启动前拒绝相应能力，不能隐瞒该路径。
- “可靠”只覆盖冻结并实测的托管进程边界。对恶意逃逸、系统外部服务、已受理远程请求不作额外保证；正常宿主调用链不能靠这些边界声明排除。

新增能力检查必须反映当前可用机制，不只检测 `process.platform`。预检失败时没有模型或 worker 启动。Windows 缺方案时该阶段保持未完成；不通过降低三平台完成门收束。

### 3.3 全局账本：一致的读、计算、追加

继续使用 `sandboxUsageDir()` 作为唯一目的地入口。工作区 SQLite 与跨项目 JSONL 各自保留权威范围，不能为了此补丁扩展迁移面。

1. 所有全局追加入口共享跨进程互斥：读取既存记录、判重、必要的差量重算与追加必须在同一临界区。锁作用于实际账本目录，包含跨月份文件的事件判重，不只锁当前月文件。
2. `appendSandboxUsage` 保持既有事件身份 `(project, runId, instance, watermark)` 及旧形记录兼容规则；不同实例的等额消费不合并，无身份历史不能凭金额伪造新身份。
3. harvest 扫描来源库可在锁外完成；apply 时须在锁内重新读取当前账本、按该来源快照重算差量。dry-run 的差量不是提交凭证。并发旧／新水位、runner 与 harvest 交错也须验证，不能只修相同水位的重复。
4. 锁须有有界等待、可诊断错误、崩溃恢复与保守的旧锁处理。不能仅凭文件年龄删除仍活跃的锁；不得用进程内 Promise 队列冒充跨进程互斥。锁内不运行模型、网络、子进程查询或持有工作区 SQLite 写事务。
5. 保留普通文件／符号链接守卫及私有权限；避免固定共享临时文件。追加成功、回执丢失后的重放不得重复计费。磁盘满、权限错误、写中断半行、账本不可读或损坏须可见，不得当完整空账或静默修写历史。
6. 如并发顺序暴露来源身份或差量协议的根本不足，在 R0/R3 记录反例并补足向前兼容协议；不以“仅串行操作”掩盖已确认的多进程使用面，不自动更改真实历史行。

### 3.4 失败回执与低风险修复

- spool 文件名使用项目和运行／事件身份的稳定安全摘要；内容保留可诊断身份。防止项目同名、路径字符归一化、runId 复用造成覆盖。相同事件重复失败可更新其回执，不能吞另一事件。
- **spool 仍是缺口回执，不自动升级为重放队列。** 现有回执不含完整计量载荷；不能凭它重新构造消费或自动重跑模型。实际账本重试仍从权威运行档／来源库取证，幂等性由入账面保证。
- 兼容读取旧 `.spool-pending-<runId>.json` 并维持缺口诊断；不自动删除、伪造已丢失项目的回执，也不因某次追加成功就清除历史 pending。身份不足时如实报告，保留人工核对路径。
- D2 沿用 0.6.1 的 provenance 编解码契约，定义字符串／对象／空值的交付派生规则；结构不支持时显式拒绝，不能隐式字符串化。D3 复用实际目的地解析，测试覆盖目录覆盖变量。

## 4. 实施阶段与文件责任

各阶段为顺序验收单元，可拆成小变更审查；实施已授权，提交仍被禁止。涉及现行语义的变化同步决策记录；阶段状态只能由新证据推进。

### R0：冻结可实现的生命周期与账本协议

**入口：** 实施启动授权；重读当前工作树与适用说明，确认与本文基线的差异。

**工作：**

1. 在隔离夹具中重建 F1/F2/F3 红检查；记录事件身份、进程退出与延迟写证据，避免仅靠 mock 返回值判定。
2. 在三平台做无需模型的最小能力验证：父子／孙进程、独立进程组、跨分段后台服务、控制器强杀与下一次启动恢复。记录真正使用的 OS 机制与可核验身份，不先假定 Node 已提供足够能力。
3. 冻结运行状态机：建议 `starting → active → stopping → cleaned`，无法确认时进入 `cleanup-pending`；明确每条边的落盘顺序、崩溃窗口、恢复互斥、lease／fence 检查和跨 CLI 上下文传递。状态名及存储位置尚未实现。
4. 冻结三平台清理宽限与测试容差，依据能力验证给出可测上限；不得将宽限设为无界。计费停止仍遵循近似限制和在途消费如实记账。
5. 冻结全局锁协议、锁顺序、事件／spool 身份和损坏读面处理；覆盖 runner 与 harvest 的交错，而非只有 append 单函数。

**文件：** [headless](../core/headless.js)、[runtime](../core/runtime.js)、[drive](../core/drive.js)、[review](../core/review.js)、[review-sandbox](../core/review-sandbox.js)、[cost](../core/cost.js)、[harvest](../scripts/harvest-sandbox-usage.mjs)；红检查进入对应 `test/`。

**出口：** 三平台机制有离线实证；实现接口、恢复协议、失败码及兼容策略可直接编码。难逆且有真实取舍的设计新建 ADR，并同步 [decisions](decisions.md) 与 [AGENTS](../AGENTS.md) 摘要／日期，遵守 AGENTS ≤12 KiB。若现有零依赖、Node ≥24 的边界内无法满足要求，提交具体失败证据与最小替代提案，本阶段不假通过。

### R1：实现进程生命周期原语

**依赖：** R0 通过。

**工作：** 增加归属／恢复模块与必要的平台适配；在 headless 中区分“单次独立调用结束即清理”和“归属于 drive、分段结束保留后台”的生命周期。实现启动登记、截止／取消传播、清理与清理后核验。旧独立评审调用不因接口重构失去现有沙盒能力。

**检查位置：** [headless 原语测试](../test/headless-primitive.contract.test.js)、[评审生命周期测试](../test/headless-review-lifecycle.contract.test.js)、[运行时测试](../test/runtime-kernel.contract.test.js)，必要时新增专门的跨平台真实进程测试文件。

**出口：** 无模型情况下证明跨段存活、最终退出、强杀恢复、管道不挂死和不误杀；清理失败可观测且可重试。不得把 `exit`／`close` 事件收到或 kill 调用成功当成全部后代已停止。

### R2：接入主会话、workers、评审与恢复入口

**依赖：** R1 通过。

**工作：**

1. 让 `runDrive` 与 `runDriveWorkers` 共用运行上下文；worker 派发前检查能力、截止、取消及清理状态。工作进程失败后的其他在途进程按既定收束规则处理，不能遗留孤儿。
2. 将上下文接入通过 CLI 发起的独立评审／复判，覆盖其独立进程组、重试、endpoint 代理及凭据清理；不能只覆盖依赖注入的测试调用。
3. 在 [queue](../core/queue.js) 的 drive 调用链与 [CLI](../cli/lzy.js) 入口接入恢复前置检查。恢复互斥须覆盖多个并发 CLI；lease reclaim、reset 等恢复操作不能清掉进程残留阻塞而放行派发。
4. 梳理 `finally` 顺序：先关派发、持久化停止状态、回收核验、记录结果，再完成租约处置；即使租约因崩溃过期，pending 仍阻止新派发。保持队列事务、预算结算与外部交付意图的现有幂等边界。
5. [status](../core/status.js)／[doctor](../core/doctor.js) 给出运行归属、清理状态、阻塞原因和实际恢复入口。JSON 只作兼容增加，不改既有字段含义；具体命令拼写与字段在 R0 冻结。

**检查位置：** [drive 测试](../test/drive.contract.test.js)、[workers 测试](../test/drive-workers.contract.test.js)、[评审运行时测试](../test/review-runtime.contract.test.js)、[OS 沙盒测试](../test/review-os-sandbox.contract.test.js)、[观察面契约](../test/status-doctor-json.contract.test.js)，以及受影响的 queue／CLI 测试。

## 5. 必需验收矩阵

下列均是未来验收，不是本次已通过项。关键检查不能 skip 后计为通过。进程判定同时使用平台归属检查与文件／心跳证据；设置有界超时、夹具 finally 清理和独立看护，测试失败也不能留下后台进程。

| 检查 | 具体场景 | 通过条件 |
| --- | --- | --- |
| P01 主链终止 | 假引擎创建子／孙进程，持续心跳并计划延迟写；分别触发预算停止、取消、异常 | 收束后无归属该运行的存活进程，宽限后无新增心跳／标记；退出原因准确 |
| P02 跨段复用 | 第一段启动本地服务并退出引擎，第二段访问同一服务，最终完成 drive | 段间服务可用，整次运行完成后服务停止；文件与普通日志保留 |
| P03 workers 与嵌套评审 | 两个 worker，各自启动后代；经真实 CLI 发起具有独立进程组的评审 | 截止／取消传播到全部登记分支；无新派发；代理及临时凭据按规则清理 |
| P04 退出与管道 | 引擎先退出、后台仍持 stdio；进程忽略温和终止；终止接口报错 | 返回有界，必要时强制回收；未证实停止时 pending，不能报告清理成功 |
| P05 绝对截止 | 接近截止才启动下一段／评审重试；截止与派发同时发生 | 子级不重置父预算；截止后的 spawn 计数为 0；回收宽限独立记录 |
| P06 前置能力 | 缺少／损坏平台清理机制，或发现未处理残留 | 主会话、worker、review 派发前具名失败，模型启动计数为 0 |
| P07 强杀恢复 | 在启动登记、active、stopping 等窗口强杀控制器，随后并发发起两个恢复／启动命令 | 遗留可诊断，恢复互斥且幂等；确认清理前无新派发；重复恢复不重跑任务 |
| P08 身份与租约 | 旧 PID 被其他进程占用、记录损坏、旧控制器仍活跃、lease 失效／reset／reclaim | 不误杀活跃或无关进程；不因租约清除放过未清理状态；fence 单调且拒绝旧写入 |
| A01 同事件并发 | 四个独立进程经屏障同时追加同一项目／run／instance／watermark | 恰好 1 行且只计 1 份用量；重放无新增，返回结果区分追加与跳过 |
| A02 身份区别 | 同 runId 不同项目、同实例不同水位、不同实例等额消费、跨月重放 | 合法不同事件均保留；同事件跨月仍只记一次；不以金额代替身份 |
| A03 差量交错 | 两个 harvest 来源快照一旧一新，交换 apply 顺序；runner 追加穿插其中 | 最终分模型／token／积分合计与权威快照一致；无重复、漏计或负差量伪修复 |
| A04 锁与写中断 | 持锁进程崩溃、等待超时、活锁不可偷；写成功后丢回执；磁盘满／权限拒绝／半行 | 可恢复或具名阻塞；重复提交不重复计费；损坏不算空账；既存行不被改写 |
| A05 spool 隔离 | 两项目相同 runId 同时失败；同项目复用 runId；相同事件多次失败；含特殊字符 | 不同缺口互不覆盖，相同事件身份稳定；pending 数与保留的回执一致 |
| A06 旧数据兼容 | 旧无 harvest JSONL、旧名 spool、字段缺失、不可读目录及错误目标类型 | 保留现行兼容及完整性诊断；无法判定的缺口不自动销账；不碰真实历史 |
| A07 D2/D3 | provenance 字符串／对象／空值及不支持形状；设置账本目录覆盖后执行 harvest | 交付来源按冻结规则读回，旧字符串兼容；输出路径等于实际写入路径 |
| G01 既有门回归 | lease/fencing、授权、评审有效性、未知计量、队列结算、SQLite floor、打包 | 既有门保持，新增检查真实进入发现范围；关键平台腿不能靠 skip 过关 |
| G02 测试隔离 | 所有进程／账本检查使用独立临时目录并核对测试前后全局目录摘要 | 用户真实账本与配置不变，结束后无夹具残留进程；不靠外部覆盖破坏测试自带隔离 |
| G03 文档 | 双语说明、发布状态、旧锚点与新恢复步骤 | `node scripts/check-docs-links.mjs`、`git diff --check` 通过，说明与平台证据一致 |

## 6. 证据、完成门与交接

实施证据默认保存在被忽略的 `artifacts/` 独立批次目录：候选源码／包摘要、OS／Node／架构、命令、脱敏环境、检查编号、开始结束时间、退出码、进程归属／回收记录、文件摘要及红绿日志。若候选未提交，记录基线提交和差异摘要；不能让不同源码共用一个“已通过”标签。

先运行受影响的聚焦检查；通过后跑全套与三平台矩阵。新的代码改动、失败或证据疑点才触发相应重跑。原计划落盘阶段仅验证文档；本次实施另行保存产品测试证据。

补丁完成须同时满足：

1. F1/F2/F3 有确定复现与修复后的真实进程／文件系统证据，D2/D3 有对应回归；没有把待确认问题写成已修复。
2. 三平台生命周期门通过，包含嵌套评审、跨段后台服务、控制器强杀恢复；能力不满足时的运行前拒绝也经过验证。
3. 历史消费和授权语义保留；全局账本异常不变成零消费；缺口可见且恢复不会重复派发／计费。
4. 全套、地板兼容、包内容和文档验证通过，当前候选与所有证据一致；原有全套 966 仅是基线，不要求用固定数量冒充新增覆盖。
5. 报告分列已实施、已验证、未验证、平台限制。离线假引擎证明进程机制与接线，不等同真实 ZCode／provider 行为；产品价值和远端请求终止仍无新增证据。

缺任一必需门，结果写为“部分完成／阻塞及原因”，不标记补丁完成，不转入发布。三平台机制无法在现有约束内落地、无法保证不误杀、或账本协议无法守住不重不漏时，带具体反例提出取舍，不自行缩小已确认目标。

交接给[原生产品价值计划](plan-native-product-value.md)的内容仅包括候选、平台能力表、生命周期和计量证据、剩余真实宿主验证项。M0 仍需自行核验真实两臂身份、授权、全尝试计量和交付协议；本补丁不能替它完成验收或启动付费运行。
