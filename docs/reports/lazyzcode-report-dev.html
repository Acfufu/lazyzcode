摘要与怎么读这份报告TL;DR↑

目标：给 ZCode 做一个 lazycodex 同款的「AI 编码工作流纪律层」，让 AI 不只写代码，而是计划 → 执行 → 拿证据 → 不做完不停。

技术结论（一分钟版）：

  • lazycodex 仓库是 MIT → 它的插件结构、技能文本可以合法改写拿来用；OmO 主仓是 SUL-1.0 → 只能学思想，一行代码都不能搬。
  • ZCode 的插件/钩子/子智能体/MCP 基建齐全（本机逐项验证过），但钩子缺口实为 6 个（逆向复核：Codex 原生 12 事件 vs ZCode 7 事件）：最关键三个 = 没有 SubagentStop、没有 PreCompact、Stop 续跑最多 3 次（且需非空注入、预算与后台通知共享）。
  • 所以推荐架构是：深循环做成 CLI 状态机（lzy loop，像 lazycodex 的 omo ulw-loop 一样），钩子只做轻触发：这正好绕开 3 次上限。
  • 仓库分三层：core/（纯逻辑，不碰 ZCode API，可单测）+ plugin/（skills/hooks/agents，ZCode 装载的部分）+ cli/（安装器、doctor、loop 状态机）。
这份报告的读法：第 2 节把所有黑话讲一遍（有图）；第 3~5 节是"别人怎么做的"（机制解剖）；第 6~7 节是"我们怎么做"（选型与架构）；第 8~10 节是"上手干"（规范、避坑、文件清单）。每节都可以单独跳读。

基础概念图解Concepts 101↑

这 6 个词贯穿全文，先弄懂它们。

① 宿主（Host / Harness）与插件（Plugin）

宿主就是 AI 编码工具本身（ZCode、Codex、OpenCode）。插件是装进宿主的能力包。ZCode 插件长这样（本机从官方插件缓存里实测的目录结构）：

my-plugin/                          # 插件根目录
├── .zcode-plugin/
│   └── plugin.json                 # 清单：名字、版本、技能目录、MCP 服务…
├── skills/                         # 技能（给 AI 看的操作手册，Markdown）
│   └── my-skill/
│       └── SKILL.md
├── agents/                         # 子智能体角色定义
│   └── reviewer.md
├── hooks/
│   └── hooks.json                  # 生命周期钩子（带钩子的插件会自动启用钩子引擎）
└── .mcp.json                       # 插件自带的 MCP 服务
// .zcode-plugin/plugin.json ： 实测自官方 document-skills 插件
{
  "name": "document-skills",
  "version": "0.1.4",
  "description": "...",
  "description_i18n": { "zh-CN": "文档制作技能" },   // 原生支持双语描述
  "skills": "skills",              // 指向技能目录
  "mcpServers": { /* ... */ }
}
坑位预告（2026-09-06 修订）：官方 plugin-creator 技能的文档口径不建议把钩子写进清单，推荐放 hooks/hooks.json 文件；但引擎 v3.11.2 源码实测：清单里的 manifest.hooks 实际被支持（字符串路径 / 路径数组 / 内联对象均可，与 hooks/hooks.json 并行读取、按 realpath 去重，仅非法事件名降级为 warning）。工程上仍建议随大流放 hooks/hooks.json，但"直接照搬清单写法会翻车"的说法已过时。

② 技能（Skill）：给 AI 看的操作手册

一个 SKILL.md = frontmatter（名字 + 描述）+ 正文指令。平时不占上下文，命中时才被读入，所以叫"静态知识，零运行时成本"。用户可以用 /技能名 直接调用（相当于自定义斜杠命令）。

---
name: ultrawork-z
description: 当 prompt 含 zw/ulw/ultrawork 时激活的纪律模式指令…
---
# 角色与铁律
- 本轮第一条用户可见输出必须是：ULTRAWORK MODE ENABLED!
- 先做轻重分级（LIGHT/HEAVY），只许升档不许降档
- 测试全绿 ≠ 完成：每个验收点必须有真实表面证据…

③ 钩子（Hook）：固定时机的打卡机

ZCode 支持 7 种事件（schema 来源：官方 zcode-guide 的 diagnosing-hooks 技能；2026-09-06 已经引擎 v3.11.2 源码逐条复核，以源码为更权威事实源——文档存在滞后）。钩子进程从 stdin 收 JSON、往 stdout 写 JSON（或用退出码：0=放行，2=拦截，Stop 上的 2 = "不许收工、强制续跑"）：

事件触发时机matcher 匹配什么能干什么
SessionStart会话启动/恢复/压缩(compact)/清空startup / resume / clear / compact往对话里注入上下文（additionalContext）；PreToolUse 可返回 allow / ask / deny；Stop 可请求"再跑一轮"（≤3 次，且必须带非空注入内容——输出空 JSON 永不续跑；3 次额度与后台任务通知共享）
UserPromptSubmit用户发出消息prompt 文本（正则）
PreToolUse / PostToolUse工具调用前 / 后工具名（正则，注意大小写敏感；Task↔Agent 互为别名）
PermissionRequest / PostToolUseFailure权限请求 / 工具失败工具名
StopAI 结束回合时回复预览文本续跑请求（≤3 次）：我们的轻续跑入口；exit 2 = block = 强制续跑（reason 注入为上下文）
// hooks/hooks.json ： 插件钩子示例
{
  "hooks": {
    "UserPromptSubmit": [
      { "matcher": "\\bzw\\b|\\bulw\\b|ultrawork",
        "hooks": [ { "type": "command",
                     "command": "node \\"${ZCODE_PLUGIN_ROOT}/hooks/ulw-bootstrap.mjs\\"",
                     "timeout": 10 } ] }   // timeout 单位是【秒】；process 型的 timeoutMs 才是毫秒
    ],
    "Stop": [
      { "hooks": [ { "type": "process", "command": "node",
                     "args": ["hooks/stop-continue.mjs"], "timeoutMs": 5000 } ] }
    ]
  }
}

④ 子智能体（Subagent / Agent 工具）

主 AI 可以派"分身"去干活，分身干完只把结果带回来，不占主对话的记忆。插件可以提供角色定义文件（本机实测自 document-skills 的 agents/judge.md）：

---
name: lzy-plan-reviewer
description: 敌意式计划评审：只找漏洞，不夸人
tools: [Read, Bash]      # 工具白名单：最小权限原则
color: red
---
你是计划评审员。逐条检查计划：有没有未决歧义？验收点可观测吗？
输出：每条问题一行（类别 + 证据 + 建议），最后给 PASS / FAIL。
与 Codex 的关键差异：ZCode 的 Agent 工具没有 agent_type、fork_context 参数；通信靠 SendMessage，支持 run_in_background。lazycodex 技能文本里所有 spawn_agent(...) 示例，移植时都要改写成「派发消息自带完整角色说明」的形式。

⑤ MCP ： AI 的"外设插座"

Model Context Protocol：让 AI 调用外部工具服务的标准协议。可配在用户级（~/.zcode/cli/config.json 的 mcp.servers，本机已见 codegraph / context7 / filesystem / github 等）或插件级（.mcp.json）。好消息：你本机已经装了 codegraph 代码索引 MCP：lazycodex 里最重的组件之一我们直接白嫖现成的。

⑥ 证据（Evidence）：整套体系的灵魂

lazycodex 的铁律："TESTS ALONE NEVER PROVE DONE"（测试全绿也不算完）。每个验收点必须绑定「真实表面」的证据：HTTP 接口返回、浏览器截图、CLI 的 stdout、数据库 diff……并且证据要绑定代码快照：

git rev-parse --short "HEAD^{tree}"   # 证据记录的是"哪棵代码树"上取的证
# 代码一变（tree hash 变了），旧证据作废，必须重取：不许"翻旧账盖新章"

lazycodex 机制解剖How It Works↑

图 1 · 工作流闭环：技能是"剧本"，钩子是"监督"，状态目录是"存档点"，证据是"验收章"

三个最值得抄的机制设计

机制一：技能文本 = 宪法（行为契约）

lazycodex 的 SKILL.md 不是"建议"，是可执行的契约，而且满是防模型耍滑的硬约束（摘自原文）：

  • 强制开场标记：本轮第一条用户可见输出必须是 ULTRAWORK MODE ENABLED!：让"模式是否生效"对用户可见、可审计；
  • 一次性分级、只升不降（tier triage）：开工时定 LIGHT/HEAVY 档并记录理由，"ratchet up only"：防止模型为省事降标准；
  • 风险清单触发升档：改了鉴权/支付/并发/迁移代码，强制升 HEAVY；
  • "与本文冲突时以本文为准"：技能文本里显式声明优先级，防止模型被别的上下文带偏。

机制二：计划文件的「行语法」+ 脚手架脚本（防手滑）

计划不是随便写的 Markdown。实现项必须匹配 - [ ] N. 标题（N 是正整数），终验项必须匹配 - [ ] F<数字>. 标题，且必须顶格写在 ## Todos / ## Final verification wave 小节里。写完还要跑结构自检：任何"用普通段落或 bullet 冒充任务"的行都会被抓出来。
计划文件由脚本生成（scaffold-plan.mjs --draft-only 先出草稿 → 用户批准 → 再落正式文件），脚本幂等（重跑不覆盖）：人工手写的计划天然有格式噪音，机器生成的才好被程序解析和勾选。

机制三：子智能体通信协议 + 等待退避

  • 每个派发消息以 TASK: 开头，必须写明 DELIVERABLE（交付物）/ SCOPE（边界）/ VERIFY(验收)；
  • 长任务的孩子要主动汇报：WORKING: 任务名 - 当前阶段；卡死才许 BLOCKED: 原因；
  • 等待退避：轮询间隔翻倍、上限 ~5 分钟，不许空转刷轮询；超时 ≠ 孩子死了（只是没新消息），不许贸然杀掉重开；
  • 默认 fork_context: false（冷启动，不带父对话）：子智能体上下文自包含，省钱且不受主对话噪音干扰。

钩子缺口与架构对策Gaps & Countermeasures↑

逆向复核更新：Codex Desktop 原生钩子为 12 事件，ZCode 7 事件共缺 6 个（初版报告写 2 个）。最关键的三个缺口如下，每一个都影响架构选型。

缺口lazycodex 怎么用的ZCode 现状我们的对策
无 SubagentStop
（子智能体结束事件）		校验执行者证据、触发 start-work 续跑不存在该事件移到主循环：Agent 工具返回后，由主流程技能负责校验交付物；后台智能体用 run_in_background + 完成通知
无 PreCompact
（上下文压缩前）		压缩后重置缓存/提醒（3 个 post-compact 钩子）无该事件，但 SessionStart 的 matcher 支持 compact用 SessionStart(matcher:"compact") 做"压缩后恢复"：重读 brief + 计划 + 目标状态 → 接着干（ulw-loop 本来就要求 compaction 后先重读状态）
Stop 续跑 ≤ 3 次靠 Stop/subagent-stop 跑 100~500 轮循环硬上限 3 次；需非空注入（输出空 JSON 永不续跑）；额度与后台任务通知共享深循环下沉到 CLI 状态机（lzy loop），Stop 钩子只做轻续跑且预算与后台通知互相预留；见下图
另缺 4 个（影响小）
SessionEnd / Interrupt / SubagentStart / PostCompact		中断落盘审计、压缩后清理、子代理起始守卫四事件均不存在不影响 CLI 状态机结论（反而强化）；SessionEnd / Interrupt 若未来补齐可用于"中断落盘"审计——P3 观察项

四条实现路线的优劣势（技术视角）Build Options↑

产品视角的完整版在 PM 报告 §5；这里补开发者最关心的：每条路实际要写/改多少东西。

路径 A · 等官方（不推荐，只观察）

  • 技术上：官方明确"对跨宿主统一抽象持怀疑态度"，新适配器哲学是"让 AI 一次性写出来"：即使做了也未必有 ZCode 版。
  • 我们的动作：订阅 ROADMAP 变更（每季度看一次即可）。

路径 B · Fork OmO 引擎写适配器

  • 优：19 个 core 包直接 import（状态机/规则引擎/技能加载器都是现成库）。
  • 劣：SUL-1.0 传染（衍生品不能开源再分发）→ 对我们一票否决；core 包正处"搬家期"（ROADMAP 自述），API 不稳；memory-core 等重资产在 ZCode 有原生替代，搬来是负资产。

路径 C · 以 lazycodex（MIT）为底稿

  • 可直接改写：插件清单结构、26 个技能的行为契约文本（改工具面词汇）、钩子配置思路、安装器/doctor 模式、契约测试的组织方式。意外利好（源码复核）：ZCode 插件发现层兼容四种清单风格（.zcode/.claude/.codex/.cursor-plugin），清单可能免改名装载（待真机验证）。
  • 必须重写：所有 spawn_agent / multi_agent_v1|v2 示例 → ZCode Agent 工具语义；钩子事件映射（Codex 7 类 → ZCode 7 事件，名称对不上）；循环架构（见 §5）。
  • 工作量直觉：技能文本约 70% 可保留骨架、30% 需逐句翻译工具面；TS 组件大部分不搬（ZCode 有原生替代）。

路径 D · 全自研（推荐主路径）

  • 优：许可证干净可开源；为 ZCode 而生（内置记忆/codegraph/computer-use 直接整合）；无上游 rebase 负担。
  • 劣：工作量最大；没有 68.7k stars 背书，冷启动靠文档与 demo。
  • 降工作量关键：照 C 的文本骨架写、照 B 的分层切目录、按 §8 规范执行："自研"指代码原创，不指从零发明。
推荐组合（技术执行口径）：目录与代码 = D（自写）；技能文本初稿 = C 改写（MIT 合法，逐文件登记来源）；架构思想 = B（core 不碰宿主 API）；上游动态 = A（观察）。

工具面翻译对照表（写技能文本时手边常备）

实现规范与避坑清单Conventions & Pitfalls↑

规范一：表达层级 Skill > MCP > Tool > Hook（OmO 官方设计宪法）

能用技能文本（Markdown）解决的，不写 MCP；能写 MCP 的，不做宿主工具；前三层都覆盖不了，才写钩子。理由：技能是静态文本（零运行时、最好测、最好改），钩子是注入 AI 循环的"手术刀"（最容易引发竞态与死循环）。自检问题：这个功能"不在线时会不会世界崩塌？"不会 → 别放钩子。

规范二：子智能体派发协议（改写自 lazycodex，适配 ZCode）

/* 每次派发消息的结构化模板 */
TASK: 实现用户模块的注册接口
DELIVERABLE: src/routes/register.ts + 对应测试 + 运行证据（curl 输出）
SCOPE: 只许改 src/routes/ 与 src/models/user.ts；禁止动鉴权中间件
VERIFY: ① 测试红→绿 ② curl POST /register 200 且库里出现记录（贴输出）
背景材料：AGENTS.md 的「路由约定」一节；参考 src/routes/login.ts 的既有模式

/* 长任务的孩子要主动汇报 */
WORKING: 注册接口 - 正在补集成测试
BLOCKED: 仅在无法推进时（附原因）

/* 主流程等待规范 */
- 轮询间隔翻倍退避，上限 ~5 分钟；超时≠孩子死了，只是没新消息
- 只有三种情况允许判死重派：完成但没交付物 / 持续 BLOCKED / 进程确实不存在
- 重派必须缩小任务（更小的 SCOPE），不许原样重试

避坑清单：ZCode hooks 的 12 个坑（实测文档压缩版）

#坑正确姿势
1配置文件钩子写了不生效非插件钩子默认禁用：配置里要 "hooks":{"enabled":true,...}；插件钩子自动启用
2事件名想当然只有 7 个：SessionStart/UserPromptSubmit/PreToolUse/PermissionRequest/PostToolUse/PostToolUseFailure/Stop。写 SubagentStop/PreCompact = 永不触发
3matcher 不匹配大小写敏感正则；"bash" 匹配不到 Bash；坏正则=静默永不匹配；别名 Task↔Agent、Write/Edit←ApplyPatch
4permission denied脚本要 chmod +x，或用 bash "${ZCODE_PLUGIN_ROOT}/hooks/x.sh" 绕开执行位
5模板变量没展开只认 ${ZCODE_PROJECT_DIR}/${CLAUDE_PROJECT_DIR}/${CLAUDE_SESSION_ID}；${ZCODE_PLUGIN_ROOT} 仅插件钩子可用
6超时单位写错command 型 timeout 单位是秒；process 型 timeoutMs 是毫秒且优先级更高；写反 = 秒变毫秒瞬间被杀
7command / process 字段混用process 只收 command+args+timeoutMs；command 收 command+shell+timeout(+Ms)；混了整个钩子被丢弃
8stdout JSON 校验失败schema 严格：多余 key 直接废弃输出；只输出认识的 key，或干脆不输出（空输出合法，靠退出码）
9以为 async 影响注入async: true 生效为后台 fire-and-forget（v3.11.2 源码实测，文档滞后）：不阻塞回合，但 stdout 输出被丢弃、不注入。同步注入类钩子仍必须快（预算 < 几秒）；异步适合取证归档（截图/日志）不占主循环时间
10跨平台翻车command 走 shell（POSIX 语法在 Windows 挂）；优先 process 型（参数数组，无 shell）
11会话被意外阻断退出码 2 在三处有语义：PreToolUse / PermissionRequest = deny；Stop = block = 拒绝结束回合、强制续跑（reason/systemMessage 注入为上下文，同样受 3 次预算约束）；其余事件 = 不继续；其他非零 = 报错；默认放行用 0
12以为第三方钩子有信任门当前插件钩子直接执行，但引擎已灰度工作区钩子信任门（workspace_hooks_pending_trust / blocked_by_policy / snapshot_mismatch 等策略码，文档未提）：我们的安装器坚持「装插件」，永不改写用户 config.json；钩子只做轻量、确定、可快退的事

已知失败模式与防御设计Failure Modes↑

上游（OmO/lazycodex）真实踩过的坑 + 社区反馈的问题，逐条给出我们在设计层面的防御。

失败模式上游实锤我们的防御设计
评审代理沉默：审批关口等评审，评审不回话，任务挂起lazycodex Issue #19：codex-ultrawork-reviewer 在定向提示后仍无响应派发协议含显式 ack：收到任务先回 ACK；等待方按退避轮询，超时三次未动 → 判死并降级（主流程自己评审 + 在状态里记录降级原因），永不无限等待
续跑循环抽风：todo 续跑出现重复/怪行为Reddit 多帖（"todo continuation loop causing weird behavior"）循环状态只存磁盘（.lazyzcode/loop/state.json），每步幂等（step_id 去重）；续跑先读状态再行动，禁止凭记忆续
Token 失控：3× 消耗、额度烧穿glukhov.org 实测 ~3×；Reddit "两三个任务烧光 4 小时额度"① 轻重分级默认 LIGHT，升档要理由（只升不降）；② 预算护栏：PreToolUse 钩子统计本会话派发/取证次数，超阈值注入"降档"提醒；③ 子智能体默认冷启动（不带父对话）
压缩失忆：长任务中途上下文被压缩，接着干就跑偏ulw-loop 的规则就是为此而生（"compaction 后先重读 brief+goals+ledger，never re-plan from scratch"）SessionStart(compact) 钩子注入恢复提醒；恢复动作写进技能的"必做第一步"；状态全在磁盘
主循环注入竞态：多个钩子抢同一停止/空闲边沿，重复注入消息OmO 官方《Why Not OpenCode-Native》整节反思钩子之间单一职责、互不重叠（触发归 UserPromptSubmit、守卫归 PreToolUse、续跑归 Stop）；同一事件上最多挂一个我们自己的钩子；钩子永远只做"注入提醒/放行拦截"，不做业务逻辑
伪完成：测试绿了就说做完上游铁律 "TESTS ALONE NEVER PROVE DONE"终验波（F 项）强制真实表面证据；证据带 tree hash，代码变了自动作废重取
