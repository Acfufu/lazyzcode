## 发现

### V024-R1-A-1 · P2 · 干净收束的清理相移除工人 worktree 但不移除 subject——悬空 subject 使该目标后续 finish 被完整性闸门确定性拒绝，恢复指引错位
证据：`core/drive.js:992` `if (outcome.ok && outcome.cause !== "merge-conflict") cleanupPhase();` 在 **ok:true 干净收束**（墙钟尽/预算尽/stuck/波数尽/积分尽，goal 仍 executing、仍有 pending 步）时也触发；`cleanupPhase`（:716-728）删 worktree/分支/home 但**不删 subjects**（:712-715 注释只论证了 done 态不可调 removeSubject，未覆盖 executing 态收束——此时 `removeSubject` 恰恰**可调**，core/loop.js:764-792）。subject 根已删后：`fingerprintSubjects` 把缺失根以 `"missing"` 入串（loop.js:703-718）→ 取证可过，但 finish 第四拒按 missing 根硬拒（loop.js:1714-1731，恢复指引=`lzy loop subject remove`）。后果链：干净收束快照写「复归：zw 继续」→ 下一次 drive/交互推进到 finish 必拒；drive 侧 finish 失败 riskNote（drive.js:836-838）把常见因错归为「某 subject 脏：工人 worktree 留了未提交物——人工清理该 worktree」，对 missing 根场景是错误处方（worktree 已不存在，无从清理）。多波目标（波数尽是常态出口）第二次 run 起必然命中。修法一句话：干净收束（非 done、非 merge-conflict）的清理相应先对本 run 的 worktree subject 逐个 `lzy loop subject remove`（executing 态合法）再拆 worktree，并在快照 riskNote 写明；或至少把 finish 失败 riskNote 的归因改为三态（脏/missing/其它）。
严重性注记：闸门本身按设计 fail-closed、无数据丢失、恢复出口存在，故取 P2 不取 P1；「拿不准就高」的另一半理由（workers 模式恢复主路径确定性被断）已在此声明。

### V024-R1-A-2 · P2 · 启动回收对兄弟根 `<host>-fast/` 下**任意**条目做无差别 `rmSync -rf`——无所有权标记、无名称形态校验、不盘点未提交 salvage
证据：`core/drive.js:662-678`：`for (const name of readdirSync(wtRoot)) { if (name === runId) continue; rmSync(stale, { recursive: true, force: true }); ... }`。唯二豁免是「等于本 runId」；`fast-\d{14}`/`fast-*.logs` 形态校验、所有权标记文件、salvage 盘点一概没有。任何用户/工具放在 `<repo>-fast/`（一个自然的兄弟目录名）里的内容会在下一次 `drive --workers` 启动时被静默递归删除——「无活跃租约关联」只是从本 goal 租约推出的推断，对目录内容不构成核验。同时注释声称「未合并残留分支=salvage 族资产保留」（分支层 salvage），但 stale runDir 内工人**未提交**改动随目录整体销毁、无 ADR-0009 盘点。修法一句话：只删匹配 `^fast-\d{14}(\.logs)?$` 的条目，删除前列目录清单入回收日志（或 salvage 存根）。
严重性注记：若按合同 P0「数据损坏」的字面可辩 P0；取 P2 因前置条件=用户自有同名兄弟目录、且损毁面在仓库与账本视野之外。

### V024-R1-A-3 · P3 · 屏障重锚块三缺陷：`readGoal` 裸奔破收束不变量 + 失败后不 `break` 致 windDownW 逐项重入 + `??` 链吞 stderr（fb61809 同族漏修点）

### V024-R1-A-4 · P3 · `drive.claimFresh` 复制认领新鲜谓词且与 core `isClaimFresh` 漂移——未来时间戳异常标记在分波侧被当「在场」，永久排除出分派池
证据：`core/drive.js:540-543` `return Number.isFinite(at) && now - at < WORKER_CLAIM_TTL_MS;` 对 `at > now`（时钟回拨/VM 恢复/手改）判**真**（在场）；core 单源 `isClaimFresh`（loop.js:1404-1411，ADJ-14）对 `at > now` 判**假**（异常标记=不新鲜、可再认领覆写）。后果：一条未来时间戳的认领在 workers 分波里使该步永久不入 pool（而同槽其他语义判定它可认领），波波空转 → 两波后以「无推进（stuck）」误判收束。实测复核：node 下 `now - futureAt < TTL === true`。`blockedByLocal`（:545-550）同样复制了 core `blockedBy`（loop.js:1424-1429，逐字段同、暂无漂移）。修法一句话：drive 导入 core 的 `isClaimFresh`/`blockedBy` 单源（导出即可），删本地复制。

### V024-R1-A-5 · P3 · 工人中途退场留下的步级认领永不被自家调度器再分派或释放——后续波空转、stuck 收束因失真，快照不指 `--release`

### V024-R2-B-1 · P1 · cleanupPhase 在 ok:true 非 done 收束上静默销毁工人 worktree 的未提交内容
