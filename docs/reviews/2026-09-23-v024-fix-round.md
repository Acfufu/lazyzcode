## §2 执行期新发现（超出评审报告，已在当步记账）

1. **清理相必须在租约窗口内跑**（N1 实作时发现）：摘 subject 是经 CLI 的带 fence 写命令，而 drive 的 `finally` 在收束后即释放租约——「释放后再摘」会被 `guardFence` 拒，于是「已修但仍悬空」。整相移入 try 内、release 之前。**这一条评审报告未预见**（其建议只写「cleanupPhase 前逐个 removeSubject」）。
2. **⑨ 夹具的同步假工人把两名工人串行化**（N3 实测）：`Atomics.wait` 阻塞事件循环 ⇒ `各工人耗时=1606/705ms`（900ms 的工人被量成 900+700），「墙钟取 max 不 sum」在该夹具下**不可观测**——旧断言窗失效实为**双重**（窗口无判别力 + 夹具量到的是 sum 形）。改异步假工人后才分离（1800 vs 3200）。
3. **不可读目录被并入「空目录」**（N10 自查）：我给 attest-trailer 新增的「零尾注+目录有文件=warn 报数」分支首版把 readdir 失败静默当作 0 件，于是权限问题报成「两态皆空」——被自己新写的测试揪出并修正。
4. **v023 报告头行的正确值是 39 而非 3**（N8 自查）：ADJ-38 只指出算术滑差（38+2=40≠41），我先按「部分成立 2→3」修，逐行重数 §3 表后确认错的是「成立 38」——最终按 39 + 2 = 41 订正（订正说明入报告头行）。

## §6 可复用教训（下轮别再踩）

1. **收束相的写命令必须留在租约窗口内**：drive 的任何「收束后整理」（摘 subject、写标记）若发生在 `finally` 释放租约之后，带 fence 的 CLI 写会被 `guardFence` 拒——表现是「代码看着修了、状态仍悬空」。凡收束相要经 CLI 写盘，就把它放在 `try` 内、release 之前（本轮 N1 实作时才发现，评审报告未预见）。
2. **契约夹具的假引擎必须是异步的**：`Atomics.wait` 忙等会阻塞事件循环，让「并发」的两名工人实测串行（900ms 的工人被量成 1606ms）——于是「墙钟取 max 不 sum」这类断言量到的是 sum 形。凡测并发语义的夹具，用 `await setTimeout` 而不是同步忙等。
3. **判据的读面必须与门同源**：INV-08 的门在 125bbdd 收窄到「现行红」，而 `evidence list` 仍在全量遍历——读面说「会被拒」、门其实放行。凡门有一次口径收窄，顺手 grep 所有同概念读面（展示、doctor、报告），否则读面成为第二真相。
